## The one thing that is broken

`test/passerby_picker_voice_test.dart` — all four tests fail with:

```
A Timer is still pending even after the widget tree was disposed.
```

**Why.** `PasserbyMessagePicker._autoListenLoop` is an infinite loop by
design: while the sheet is open it narrates, waits out
`SttService.narrationSettle` (600 ms), listens, and repeats. On a device that
is correct — it keeps re-prompting for as long as the user has the sheet up.

In the test the scripted recogniser returns instantly once the script runs
dry, so the loop spins on that 600 ms timer, and a `Future.delayed` still in
flight at teardown fails the test.

It was *passing* before this session. What changed: removing the five-second
cancel window (below) made each turn of the loop much shorter, so the loop now
reaches its dry state inside the test's pump budget where it previously did
not.

**Two attempts already made, both insufficient** — do not repeat them:

1. Bounded `tester.pump()` calls instead of `pumpAndSettle()`. Necessary, but
   not sufficient on its own. Keep it: `pumpAndSettle` never returns against a
   repeating timer.
2. Popping the sheet at the end of `openPicker` and pumping past one more
   settle. Still fails — the loop appears to re-schedule before the `mounted`
   check retires it.

**Suggested next approach**, in order of how likely they are to be right:

- Give `_autoListenLoop` a cancellable delay rather than a bare
  `Future.delayed` — hold the `Timer` in a field and cancel it in `dispose()`.
  That fixes the test *and* is the more correct behaviour: right now the
  widget can be disposed with a timer still pointing at it.
- Or have `_ScriptedStt` return a never-completing future once the script is
  exhausted, modelling a real recogniser that blocks rather than one that
  returns instantly. That makes the fixture honest instead of working around
  it.

Prefer the first. The second hides a real disposal gap.

## What is in the working tree, and why

All of it is uncommitted. Everything except the picker test passes — run
`flutter test` to confirm the blast radius before touching anything.

### 1. The five-second cancel window is gone for dictation

Asked for directly: *"remove the 5second cancel window, you already read back
response for confirmation"*.

`VoiceCancelWindow.readBackOnly` is new — it speaks the read-back and returns
immediately, with no waiting window and no listen. The hazard hub and the
passer-by picker now call it instead of `run`.

**The Magic Button deliberately still calls `run`.** This was a judgement
call, flagged to the user and not objected to: for dictated prose a mistake is
cheap (a garbled hazard report still reaches a human and still clusters), but
for the emergency the mistake is messaging and telephoning somebody's family,
and it cannot be undone by looking at the screen. If it is ever decided the
emergency should lose its window too, that is a one-line change in
`emergency_service.dart` — but it should be a decision, not a tidy-up.

### 2. Cancelling a trip now actually cancels it

Reported: *"Cancel the trip to Dhaka"* was answered with *"Cancelled your trip
to Dhaka"* while the route stayed active and the map kept drawing it.

There was no `cancel_route` intent **at all**, so it fell through to Gemini,
which described a state change it had no way to make. This is item 22's
invented-status problem with real consequences.

Added:

- `_matchCancelRoute` in `LocalIntentMatcher`, ordered *before* both
  `_matchRouteChange` and `_matchRoute` — "cancel the route" contains "the
  route", and "cancel the trip to Dhaka" names a destination.
- `ChatController._cancelRoute`, which stops the narrator silently, clears the
  route, and says so. Handled in the controller rather than the executor for
  the same reason `trigger_emergency` is: the executor has no route to clear
  and no navigator to stop.
- A `cancel_route` tool declaration for Gemini, worded to distinguish it from
  `request_alternative_route` (same destination, different road) and
  `replan_route` (same destination, new start).
- `routeCancelled` / `routeNothingToCancel` strings.
- `test/cancel_route_test.dart` — **passing**, 13 tests.

### 3. The map closes when the trip is cancelled

Reported: *"map should close if user says the trip is cancelled, right now it
remains still"*.

`SplitModeDashboardScreen`'s `ref.listen` on `pendingRoute` used to only ever
*open* the map, on the reasoning that somebody who deliberately hid it should
not be overruled. That is right for a rebuild and wrong for a cancellation, so
it now closes the map when the route goes from non-null to null.

### 4. An unbounded spin in the Show Screen overlay

Found while chasing the test hang, and worth keeping regardless.

`PasserbyHelperOverlay._listenForDismissOnDeviceLoop` re-invoked itself with
**no delay** whenever `listenOnce` returned immediately — which happens for
real whenever the recogniser cannot start (denied permission, no recogniser
installed, a session that dies on arrival). It now waits 400 ms between
attempts, the same guard the hazard hub's listen loop has always had.

## Latency — analysed, not yet acted on

Measured in one session on one device: Gemini round trips of **1486 ms,
19883 ms, 20204 ms, 28867 ms**, against **17 ms** for a locally-matched
command. A 20x spread with nothing changing is variance, almost certainly
network.

Already shipped: a spoken "Still working on that…" after three seconds, and
time-to-first-chunk logged separately from the total so a slow *start* (the
model thinking) can be told from a slow *stream* (a long answer).

Not yet done, best first:

1. **Widen the local matcher.** "Report a hazard" went to Gemini only because
   Cloud STT heard *"People of the hazard."* Local matching is 17 ms and needs
   no network; tolerating mis-transcriptions there removes the round trip from
   the common path entirely. Biggest win available.
2. **Speak the first sentence as it streams.** The chat bubble already fills
   progressively; TTS waits for the whole response. For voice users that alone
   would cut *perceived* latency to roughly the first-chunk time.
3. Drop `maxOutputTokens` from 1024 — on a 3.x thinking model a large budget
   invites longer internal reasoning. Guesswork until the first-chunk logging
   says whether the delay is before or during the response.
4. Compare wifi against mobile data before assuming it is Google's end.

## State of the wake word, so it is not re-litigated

Two separate bugs, both now fixed, and it is worth not confusing them again:

- **Item 6** — the assistant's own reply took permanent audio focus and
  stopped its own microphone. Confirmed fixed on device: 8 detections out of
  8 in one session, every restart on time.
- **Item 24** — the detection threshold was 0.5 when real attempts were
  scoring 0.30-0.34. Lowered to 0.30 and made tunable with
  `--dart-define=WAKE_WORD_THRESHOLD_PCT`. **Not yet confirmed on a device**,
  and the thing to watch is false positives: background never exceeded 0.003
  in the measured session, but that is one voice, one room, one session.

The real fix for both remains a real wake-word model. `hey_jarvis_v0.1` is
synthetic English clips, is not the app's own wake phrase, and is not tuned
for Bangladeshi speakers.
